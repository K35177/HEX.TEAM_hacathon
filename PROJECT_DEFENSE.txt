МАТЕРИАЛ ДЛЯ ЗАЩИТЫ ПРОЕКТА
Версия проекта: 0.7.2

======================================================================
1. СУТЬ ПРОЕКТА В ОДНОМ ПРЕДЛОЖЕНИИ
======================================================================

HEX Acoustic Modem передаёт произвольные файлы непосредственно через звук:
передающий компьютер превращает файл в акустический FSK-сигнал, принимающий
компьютер записывает его микрофоном, исправляет допустимые ошибки и сохраняет
файл только после полной проверки целостности.

Короткий слоган:

    «Передача файлов там, где нет сети, но есть динамик и микрофон».

Корректное позиционирование:

    Кроссплатформенный лабораторный прототип акустического файлового
    транспорта с нативным DSP-ядром, FEC и проверкой целостности.

Некорректное позиционирование:

    Не следует называть текущую версию production-ready модемом,
    гарантированно кроссплатформенным продуктом или заменой Wi-Fi/Bluetooth.

======================================================================
2. КАКУЮ ПРОБЛЕМУ МЫ РЕШАЕМ
======================================================================

Обычная передача файлов требует сети, Bluetooth, кабеля, флеш-накопителя,
драйверов или сопряжения устройств. Наш проект показывает альтернативный канал:
звук, который поддерживается практически любым ноутбуком и телефоном.

Где идея особенно уместна:

- изолированные и air-gapped среды;
- аварийная передача небольших данных без доступной сети;
- устройства без общего сетевого интерфейса, но со звуковым трактом;
- учебные и исследовательские задачи DSP и цифровой связи;
- резервный низкоскоростной канал конфигурации или телеметрии;
- демонстрация полного модемного стека на обычном пользовательском ПК.

Это не массовая замена быстрым радиоканалам. Продуктовая ценность появляется
там, где важнее доступность физического канала, чем высокая скорость.

======================================================================
3. КАК РАБОТАЕТ РЕШЕНИЕ
======================================================================

Передача:

    файл
      -> имя, размер и SHA-256
      -> нумерованные пакеты с CRC32
      -> Reed-Solomon FEC и interleaving
      -> защищённый frame header
      -> chirp-преамбула и FSK-символы
      -> WAV / динамик

Приём выполняет обратную цепочку:

    микрофон
      -> поиск chirp и оценка рассогласования часов
      -> FSK-демодуляция
      -> исправление ошибок Reed-Solomon
      -> проверка CRC32 каждого пакета
      -> проверка SHA-256 всего файла
      -> безопасное сохранение результата

Архитектура разделена на самостоятельные слои:

- UI и CLI;
- transfer metadata;
- packet protocol;
- framing и FEC;
- FSK-модем;
- WAV и платформенные audio backends.

UI не реализует протокол повторно: он запускает то же C++-ядро, что и CLI.
Это уменьшает риск расхождения поведения консольной и графической версии.

======================================================================
4. ЧТО УЖЕ ДЕЙСТВИТЕЛЬНО РАБОТАЕТ
======================================================================

- Полный цифровой цикл «файл -> звук -> файл».
- Передача произвольных бинарных файлов, а не только текста.
- Chirp-синхронизация и поиск начала сигнала среди начальной тишины.
- Компенсация рассогласования аудиочасов и пересэмплирование payload.
- Пять пользовательских профилей скорости/устойчивости.
- Автоматическая попытка определить профиль на приёмнике.
- Frame v2 с семикратным защищённым заголовком.
- Reed-Solomon RS(255,191): до 32 ошибочных байтов на codeword.
- Межблочный interleaving против коротких выпадений сигнала.
- CRC32 каждого пакета и SHA-256 всего принятого файла.
- Автоматическое и ручное усиление записи.
- Остановка записи после пяти секунд относительной тишины.
- estimate: оценка времени до передачи.
- benchmark: измерение airtime, goodput и CPU-времени.
- channel-test: воспроизводимые сценарии шума, drift и clipping.
- calibrate: локальная проверка динамика, микрофона и тестового кадра.
- Безопасные временные файлы, атомарное сохранение и защита от перезаписи.
- Лёгкий одностраничный UI.
- Автономный Windows x64 EXE размером около 12,55 МБ.

======================================================================
5. СИЛЬНЫЕ СТОРОНЫ ПРОЕКТА
======================================================================

5.1. Полный вертикальный продукт

Это не отдельный DSP-алгоритм и не макет интерфейса. В проекте есть путь от
выбора пользовательского файла до физического воспроизведения и обратно,
включая протокол, контроль ошибок, диагностику и UI.

5.2. Целостность важнее ложного успеха

Программа не сохраняет «примерно похожий» файл. Результат принимается только
после пакетных CRC32 и SHA-256 всего содержимого. При сомнении попытка
отклоняется. Для файлового транспорта это правильнее тихого повреждения данных.

5.3. Коррекция ошибок реализована, а не только заявлена

Frame v2 использует RS(255,191) и interleaving. Автоматический тест с удалением
100 мс FSK-аудио восстанавливает исходные данные. Исправленные codewords и байты
попадают в диагностические метрики.

5.4. Эффективное нативное DSP-ядро

Критический путь написан на C++20. Goertzel заменил дорогие sin/cos на каждом
отсчёте, модулятор использует рекуррентный oscillator, WAV обрабатывается
блоками. На payload 18 000 байт turbo декодируется примерно за 215 мс при
эфирном времени около 164 с. CPU работает приблизительно в 764 раза быстрее
реального времени: узкое место — акустический канал, а не интерфейс или Python.

5.5. Осмысленная продуктовая метрика

Главная метрика — delivered goodput с учётом completion rate, а не рекламный
raw bitrate. Быстрая попытка, которая не восстановила файл, доставила 0 бит.
Такое определение заставляет оптимизировать реальный результат.

5.6. Лёгкий интерфейс

Tkinter выбран только для управляющей панели. DSP выполняется в C++. Нет
Chromium, Electron, web-сервера и отдельного runtime на компьютере пользователя:
Windows one-file EXE содержит необходимые компоненты внутри.

5.7. Работа без сетевой инфраструктуры

Для самого канала не нужны IP-сеть, учётная запись, облако или pairing.
Это и есть ключевое отличие от обычного файлообмена.

5.8. Диагностика и инженерная честность

Приложение показывает chirp correlation, confidence, clock/frequency offset,
clipping, auto gain и причины отказа. Неудачные WAV сохраняются для анализа.
Реальные неудачи не скрывались: они использовались для улучшения FEC,
частотной сетки и детектора окончания записи.

5.9. Безопасная работа с пользовательскими файлами

Имя очищается, существующие файлы без разрешения не перезаписываются, запись
идёт через уникальный временный файл с последующим commit. После ошибки не
должен появляться частично восстановленный файл с корректным пользовательским
именем.

======================================================================
6. ДОКАЗУЕМЫЕ МЕТРИКИ
======================================================================

Основной профиль turbo:

- модуляция: ортогональный 4-FSK;
- несущие: 1200 / 2400 / 3600 / 4800 Гц;
- symbol rate: 600 символов/с;
- raw bitrate: 1200 бит/с;
- FEC: RS(255,191) + interleaving;
- полоса рассчитана на обычные динамики и микрофоны.

Цифровой benchmark, payload 18 000 байт:

- airtime: около 164,04 с;
- goodput: около 877,9 бит/с;
- эффективность относительно raw bitrate: около 73,2%;
- decode CPU: около 215 мс.

Контрольный Duck.wav, 11 628 байт:

- расчётное время turbo: около 106,24 с (1 мин 46 с);
- прежняя исходная передача занимала около четырёх минут.

Тестовая база:

- 10 из 10 модульных тестов проходят локально;
- self-test проходит;
- turbo проходит 6 из 6 синтетических channel-test сценариев;
- покрыты clean, SNR 24 dB, drift 4000 ppm, SNR+drift и clipping;
- отдельные тесты покрывают FEC, burst dropout, clock mismatch и low SNR.

Оговорка, которую нужно произнести вслух:

    Это результаты цифрового цикла и синтетического канала. Они не являются
    доказательством 100% успешной передачи на любой паре реальных устройств.

9. ЧЕСТНЫЕ МИНУСЫ И РИСКИ
======================================================================

9.1. Реальный акустический тракт пока является главным ограничением

Windows noise suppression, AGC, echo cancellation, Bluetooth hands-free,
реверберация и неравномерная АЧХ могут разрушать FSK, даже если общий уровень
сигнала хороший. Последняя реальная запись имела нормальный auto gain x2.52,
но постоянное доминирование 1200 Гц. После выравнивания оставалось около 30%
ошибочных символов, и ни один из 62 FEC-codeword не укладывался в предел
исправления.

Как отвечать:

    «Мы доказали цифровой стек и обнаружили конкретный следующий bottleneck:
    per-tone channel estimation и adaptive equalization. Мы не выдаём общий
    SNR за доказательство пригодности каждой несущей».

9.2. Калибровка пока неполная

Текущая калибровка проверяет локальный путь «динамик этого ПК -> микрофон этого
ПК». На системах с echo cancellation собственный звук может специально
подавляться. Калибровка не измеряет АЧХ каждой несущей и не проверяет реальный
межкомпьютерный путь.

Нужно: двухсторонняя калибровка, per-tone response, noise PSD и рекомендации по
конкретному профилю.

9.3. Одна попытка — один большой физический кадр

Повреждение сверх возможностей RS приводит к повтору всего файла. Внутри нет
независимо синхронизируемых коротких physical frames.

Нужно: короткие кадры, frame number, session ID, отдельные CRC/FEC и повторный
поиск синхронизации.

9.4. Нет обратного канала

Нет ACK/NACK, selective repeat и resume. Приёмник не может запросить только
повреждённые блоки.

9.5. Нет автоматических переговоров

Receiver перебирает известные профили, но sender и receiver не согласуют
capabilities и скорость через robust control channel.

9.6. Hard-decision демодуляция

FSK-решение выбирает одну максимальную энергию. Высокий confidence может быть
ложным, если одна несущая постоянно доминирует. Нет soft decisions, adaptive
equalizer, pilot tracking и continuous timing recovery.

9.7. Передача не является полностью streaming

Sender сначала создаёт полный WAV, receiver сначала накапливает запись, затем
декодирует. Для больших файлов растут память и задержка. Нет защищённого
end-of-frame; остановка основана на пяти секундах относительной тишины.

9.8. Скорость невысока

Turbo имеет 1200 бит/с raw bitrate. Это приемлемо для небольших файлов и
резервного канала, но не для видео, больших архивов или конкуренции с радио.

9.9. Безопасность ограничена целостностью

SHA-256 и CRC обнаруживают повреждение, но не подтверждают отправителя. Нет
шифрования, MAC/AEAD, pairing, nonce и защиты от replay.

9.10. Кроссплатформенность реализована, но не полностью доказана

В коде есть Windows Multimedia, Linux ALSA через aplay/arecord и macOS
CoreAudio/afplay. Локально проверена Windows-сборка. Полной hardware matrix для
Linux/macOS нет. Корректная фраза: «кроссплатформенная реализация», а не
«гарантированная работа на всех ОС и устройствах».

9.11. Нет выбора конкретных аудиоустройств в UI

Используются системные устройства по умолчанию. На компьютере с виртуальным
микрофоном, Bluetooth-профилем или несколькими входами можно проверить не тот
физический канал.

9.12. Windows EXE не подписан

SmartScreen может показать предупреждение неизвестного издателя. Нет installer,
автообновления и коммерческой code-signing подписи.

11. РЕКОМЕНДУЕМЫЙ СЦЕНАРИЙ ДЕМОНСТРАЦИИ
======================================================================

Надёжная часть демонстрации:

1. Открыть one-file приложение.
2. Показать понятный одностраничный UI.
3. Нажать «Проверить оборудование» и объяснить, что это только discovery.
4. Через «Оценить передачу» заранее показать airtime и goodput.
5. Запустить «Самопроверка».
6. Запустить «Тест эффективности» и показать метрики.
7. Создать WAV из маленького файла.
8. Восстановить файл из WAV.
9. Сравнить SHA-256 исходного и восстановленного файла.
10. Показать channel-test и сценарии SNR/drift/clipping.

Живая акустическая демонстрация:

- использовать заранее проверенную пару устройств;
- отключить echo cancellation, noise suppression, AGC и voice enhancement;
- не использовать Bluetooth hands-free;
- выбрать маленький файл;
- сначала запустить приёмник, затем передатчик;
- использовать основной turbo только после успешной проверки тракта;
- иметь резервную цифровую WAV-демонстрацию и видеозапись успешного live-test.

Нельзя строить всю защиту только вокруг одной живой попытки. Акустическая среда
комиссии заранее неизвестна.

12. ТРЁХМИНУТНАЯ РЕЧЬ ДЛЯ ЗАЩИТЫ
======================================================================

«Наш проект — HEX Acoustic Modem. Он передаёт произвольные файлы через обычный
динамик и микрофон без сети, Bluetooth, кабеля и облака.

Пользователь выбирает файл, после чего C++-ядро добавляет имя, размер и SHA-256,
делит данные на пакеты с CRC32, применяет Reed-Solomon и interleaving и кодирует
поток в FSK-сигнал. Приёмник находит chirp-преамбулу, оценивает рассогласование
аудиочасов, демодулирует сигнал, исправляет ошибки и сохраняет файл только после
полной проверки целостности.

Мы сделали не отдельный алгоритм, а полный пользовательский продукт: CLI,
одностраничный UI, профили канала, estimate, calibration, benchmark,
диагностику и автономный Windows EXE размером около 12,55 мегабайта.

Главная метрика для нас — не номинальная скорость, а delivered goodput.
Основной turbo работает на 1200 бит/с; на цифровом тесте с 18 килобайтами
полезный goodput составляет около 878 бит/с, эффективность — 73%, а декодирование
занимает около 215 миллисекунд. Все десять модульных тестов и шесть сценариев
симулятора канала проходят.

Мы честно отделяем доказанное от планируемого. Windows и цифровой цикл
проверены, но реальный канал чувствителен к echo cancellation, неравномерной
АЧХ и шумоподавлению. Сейчас одна неисправимая ошибка требует повторить весь
файл; ещё нет ACK, selective repeat, адаптивного эквалайзера и шифрования.

Следующий этап — короткие независимо синхронизируемые кадры, per-tone training,
soft decisions, adaptive rate и повтор только повреждённых блоков. Уже сейчас
проект доказывает работоспособность полного акустического транспорта и даёт
измеряемую основу для превращения его в современный модем».

13. НЕУДОБНЫЕ ВОПРОСЫ И ГОТОВЫЕ ОТВЕТЫ
======================================================================

Вопрос: Зачем это нужно, если есть Wi-Fi и Bluetooth?

Ответ: Мы не заменяем быстрые радиоканалы. Наш сценарий — отсутствие общей
сети, pairing, кабеля или разрешённого радио. Динамик и микрофон становятся
универсальным резервным интерфейсом.

Вопрос: Чем это лучше QR-кода?

Ответ: QR удобен для небольшого статического payload и требует экрана/камеры.
Акустический канал работает непрерывно, не требует визуального контакта и
демонстрирует потоковую физическую среду. При этом QR может быть лучше для очень
коротких данных — мы этого не отрицаем.

Вопрос: Почему UI на Python/Tkinter, а не C++ или C#?

Ответ: UI только запускает команды и показывает результат. DSP и файловый путь
написаны на C++20. Измерения показывают, что CPU декодирует в сотни раз быстрее
эфира, поэтому переписывание кнопок не увеличит goodput. Tkinter не требует
Chromium и упакован в один EXE.

Вопрос: Почему передача такая медленная?

Ответ: Акустический канал узкополосный и нестабильный. Мы сознательно тратим
около 27% на FEC, заголовки и контроль целостности. Следующее ускорение должно
идти через адаптивную модуляцию и selective repeat, а не через повышение raw
bitrate ценой нулевого completion rate.

Вопрос: У вас были неудачные реальные передачи?

Ответ: Да. Они выявили частотно-селективное подавление и ложную уверенность
hard-decision демодулятора. Мы сохранили WAV, измерили ошибки каждого
codeword и исправили часть проблем. Оставшийся результат прямо указывает на
необходимость per-tone training и equalizer. Это честный инженерный результат,
а не скрытая ошибка демонстрации.

Вопрос: Почему FEC не спасает каждую запись?

Ответ: RS(255,191) исправляет до 32 ошибочных байтов в codeword. За этой
границей математической информации недостаточно. Production-транспорт должен
добавить soft decisions, более подходящий inner code и повтор повреждённых
коротких кадров.

Вопрос: Проект безопасен?

Ответ: Он проверяет целостность, но пока не обеспечивает аутентификацию и
конфиденциальность. Для production нужны pairing и AEAD. Мы не называем SHA-256
шифрованием.

Вопрос: Он действительно кроссплатформенный?

Ответ: Аудиослой реализован для Windows, Linux и macOS через общий интерфейс.
Windows проверен локально; Linux/macOS требуют CI и реальной hardware matrix.

Вопрос: Почему калибровка сказала, что устройства OK, а передача упала?

Ответ: «Динамик OK» и «Микрофон OK» означают только наличие устройств.
Калибровка тестирует короткий локальный loopback и пока не измеряет каждую
несущую. Echo cancellation может подавлять собственное воспроизведение ПК.

Вопрос: Что является главным следующим техническим шагом?

Ответ: Per-tone training и adaptive equalizer, после них — короткие physical
frames и ACK/selective repeat. Эти изменения повышают именно delivered goodput.

14. ROADMAP ДО PRODUCTION
======================================================================

Приоритет 1. Надёжность реального PHY

- training sequence по каждой несущей;
- per-tone response и noise PSD;
- soft decisions;
- adaptive equalizer и tracking;
- автоматическое исключение подавленных несущих;
- device selector и двухкомпьютерная калибровка.

Приоритет 2. Короткие независимо восстанавливаемые кадры

- session ID и frame number;
- отдельные header/CRC/FEC;
- повторная синхронизация после потери участка;
- защищённый end-of-frame.

Приоритет 3. Обратный канал

- ACK/NACK;
- selective repeat;
- resume;
- измерение retries и итогового delivered goodput.

Приоритет 4. Адаптация

- robust control channel;
- capability negotiation;
- automatic rate adaptation;
- fallback без ручного перебора профилей.

Приоритет 5. Безопасность и эксплуатация

- pairing;
- AEAD, nonce и replay protection;
- code signing;
- installer/auto-update;
- crash-safe session state;
- Windows/Linux/macOS hardware matrix и soak tests.

======================================================================
15. КРИТИЧЕСКИЙ ЧЕК-ЛИСТ ПЕРЕД ПРОВЕРКОЙ
======================================================================

Состояние репозитория на момент подготовки файла:

- main — клиентская ветка: README + автономный EXE;
- dev — исходный код и документация;
- собирать проект нужно из dev, не из main;
- dev содержит явные include <string>/<array> для переносимой сборки;
- dev содержит исправление остановки записи по остаточному шуму;
- main должен содержать one-file EXE, собранный из того же dev-коммита.

Обязательная подготовка демонстрационного компьютера:

- проверить запуск one-file EXE;
- сохранить SHA-256 релизного файла;
- отключить Windows echo cancellation/noise suppression/AGC;
- выбрать физические устройства по умолчанию;
- исключить Bluetooth hands-free;
- подготовить маленький демонстрационный файл;
- выполнить self-test и channel-test;
- заранее проверить WAV encode/decode;
- live-transfer проводить только на проверенной паре устройств;
- иметь резервную запись демонстрации.

======================================================================
16. ФИНАЛЬНЫЙ ПРОДАЮЩИЙ ВЫВОД
======================================================================

HEX Acoustic Modem ценен не рекордной скоростью, а полнотой реализации и
измеримостью. Команда построила физический канал, синхронизацию, коррекцию
ошибок, пакетный и файловый контроль, диагностику, UI и автономную поставку.

Проект уже убедительно демонстрирует идею передачи файлов через звук и зрелый
инженерный подход к ошибкам. Его слабые места находятся не в презентации, а в
известных задачах современного модема: adaptive equalization, короткие кадры,
ARQ, streaming и безопасность. Именно наличие измеренного рабочего фундамента
и честного плана развития является главным аргументом на защите.
