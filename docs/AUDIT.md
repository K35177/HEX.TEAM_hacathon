# Инженерный аудит проекта

Дата аудита: 25 июля 2026 года.

Обновление 0.5.0: реализован первый этап исправлений — receiver metrics,
`benchmark`, JSON, детерминированный channel simulator, Goertzel-демодулятор,
блочный WAV I/O, исправленный совместный поиск chirp/clock scale, более выгодные
размеры блоков и исправление Windows capture event. Критические protocol v2,
streaming, FEC и ARQ пункты остаются открытыми.

## Краткий вердикт

Проект уже является работающим лабораторным акустическим транспортом:

- файл проходит полный цифровой цикл `данные → пакеты → FSK → WAV → данные`;
- есть chirp-синхронизация, CRC32, SHA-256, профили, оценка длительности,
  калибровочная команда и UI;
- на Windows собран исполняемый файл, прошли девять модульных тестов и WAV-cycle
  для всех профилей;
- архитектура разделена на CLI, transfer, packet, framing, modem и audio.

Но это ещё не полноценный современный аудиомодем. Сейчас соединение является
односторонней передачей одного большого кадра с заранее согласованным профилем.
При одной неисправимой ошибке вся попытка отклоняется. Нет потокового приёма,
переговоров, коррекции ошибок, обратного канала, повторной передачи, адаптации
скорости, аутентификации и полевых метрик качества.

Корректное позиционирование текущей версии: **cross-platform acoustic file
transfer prototype**, а не production-ready modem.

впереди.

## Критические разрывы

### A-01. Вся передача — один монолитный аудиокадр

`create_audio_frame()` добавляет одну преамбулу и одну длину перед всем transfer
stream. Пакеты внутри содержат sync word, но приёмник не ищет его в потоке и не
может продолжить после вставки, выпадения или неверно распознанного байта.

Следствие: локальное повреждение превращается в отказ всей передачи.

Нужно: независимо синхронизируемые физические кадры с короткой преамбулой,
защищённым control header, frame number, session ID и CRC/FEC.

### A-02. Профиль согласуется вне протокола

Передатчик и приёмник должны вручную выбрать одинаковый профиль. Сам кадр не
сообщает modulation order, symbol rate, coding mode или protocol capabilities.
При несовпадении пользователь получает ошибку декодирования вместо переговоров.

Нужно: фиксированный robust control channel и handshake по модели
capability negotiation. Исторический ориентир —
[ITU-T V.8](https://www.itu.int/rec/T-REC-V.8/en), который описывает процедуры
начала и согласования data session.

### A-03. Нет потокового real-time PHY

`send` сначала создаёт полный WAV. `receive` сначала записывает заданное число
секунд, затем читает весь WAV и только потом начинает поиск. Это увеличивает
задержку и память, не позволяет остановиться по end-of-frame, посылать ACK во
время сессии или показывать настоящую статистику канала.

Нужно: callback/read-write audio stream, кольцевой буфер и state machine
`SEARCH → ACQUIRE → HEADER → PAYLOAD → VERIFY → ACK`. PortAudio документирует
кроссплатформенные устройства, full-duplex streams, latency и callback timing:
[PortAudio API Overview](https://portaudio.com/docs/v19-doxydocs-dev/api_overview.html).

### A-04. Нет исправления ошибок

CRC32 и SHA-256 обнаруживают ошибку, но не исправляют её. Параметр
`symbol_repetitions=3` увеличивает длительность тона; это не независимые копии с
majority vote и не FEC.

Нужно поэтапно:

1. защищённый control header;
2. soft metrics демодулятора;
3. convolutional code + Viterbi или Reed–Solomon;
4. interleaving против burst errors;
5. позднее — LDPC для высокоскоростного профиля.

Для структуры надёжного модемного соединения полезен
[ITU-T V.42](https://www.itu.int/rec/T-REC-V.42): establishment,
error-control operation, negotiation и orderly release.

### A-05. Нет обратного канала и selective repeat

При повреждении одного блока пользователь повторяет весь файл. Нет ACK bitmap,
NACK, таймера, повторной отправки отдельных кадров и возобновления сессии.

Нужно: сначала half-duplex TDD — передатчик отправляет окно кадров, затем
слушает короткий robust ACK/NACK. Полный simultaneous duplex пока не нужен.

### A-06. Синхронизация недостаточна для длинной сессии

Clock scale оценивается один раз по короткому chirp. В 0.5.0 исправлен совместный
поиск start/scale и подтверждены 4000 ppm в симуляторе, но это по-прежнему не
continuous tracking. Такой подход помогает в синтетическом
тесте, но не отслеживает меняющийся sample-rate offset, частотный drift или
пропуски callback buffers. Диапазон поиска ±2% не означает гарантированную
коррекцию ±2% во всех условиях.

Нужно: pilots внутри каждого кадра, continuous timing tracking, CFO/SRO metrics и
периодический resynchronization.

### A-07. Канал не оценивается и не выравнивается

Нет полосового фильтра, noise PSD, per-tone response, impulse response,
equalizer, clipping/THD analysis и multipath model. В 0.5.0 `calibrate` разделяет
noise/signal windows и выводит chirp/confidence/clock/frequency/clipping metrics,
но без noise PSD и per-tone response это остаётся диагностической оценкой.

Классические voice-band модемы выполняют training и equalization; например,
[ITU-T V.34](https://www.itu.int/rec/T-REC-V.34) включает training sequences,
equalization и trellis coding.

### A-08. Метаданные не аутентифицированы

SHA-256 подтверждает совпадение содержимого файла, но не доказывает отправителя.
Имя файла не входит в итоговый digest, а CRC не защищает от намеренной подмены.
Нет session nonce и replay protection.

Нужно: использовать готовую криптографическую библиотеку и AEAD, а не писать
криптографию вручную. Возможные стандартизованные варианты:

- [RFC 8439: ChaCha20-Poly1305](https://www.rfc-editor.org/info/rfc8439/);
- [NIST SP 800-38D: AES-GCM](https://csrc.nist.gov/pubs/sp/800/38/d/final).

Control header должен быть associated data; nonce обязан быть уникальным.

### A-09. Кроссплатформенность пока не доказана end-to-end

Наличие платформенной ветки кода не равно подтверждённой поддержке. Windows
собран локально. Linux зависит от `aplay/arecord`, macOS playback — от `afplay`.
Нет результатов CI и живых тестов на этих ОС, выбора конкретного устройства,
проверки permissions и latency.

Нужно: CI build/test matrix плюс hardware matrix с опубликованными результатами.

### A-10. Производительность не соответствует streaming-модему

- весь файл, transfer stream и аудиосигнал находятся в памяти;
- скорость профилей — 66/400/600 бит/с до заголовков.

В 0.5.0 исправлены три прежних CPU bottleneck: добавлены Goertzel/recursive
oscillator, блочный WAV I/O и блочное чтение UI. Decode ускорен в 3,5–6,5 раза
на контрольном файле и работает в сотни раз быстрее realtime. Открытый пункт —
bounded streaming buffers: пиковая память всё ещё растёт с размером файла.

### A-11. Отмена операции не гарантирует остановку дочернего audio process

На Linux/macOS CLI использует `system()` для внешних программ. UI 0.5.0 завершает
созданную process group, поэтому обычная отмена улучшена. Но надёжный контракт
`AudioStream::stop()` и проверенный cancel latency появятся только со streaming
backend.

### A-12. Нет эксплуатационной безопасности

Не определены безопасная громкость, предупреждение о слышимом сигнале,
поведение при клиппинге, приватность записи микрофона, хранение diagnostic WAV и
модель разрешений ОС.

## Что уже сделано хорошо

- endian и размеры полей определены явно;
- CRC каждого packet отделён от SHA-256 всего файла;
- файл записывается только после полной проверки;
- имя очищается от path traversal;
- временные имена уникальны;
- FSK configuration валидируется относительно Nyquist;
- слои позволяют развивать PHY и transport без архитектурной перестройки;
- есть детерминированные тесты framing, drift, FSK, transfer и hashing;
- `estimate` заранее раскрывает реальную низкую скорость и стоимость по памяти.

## Исправленные формулировки документации

Следующие утверждения нельзя трактовать как production guarantees:

- «поддерживает Windows/Linux/macOS» означает наличие backend code и build
  matrix; полный hardware test пока выполнен не на всех ОС;
- «компенсация ±2%» означает диапазон алгоритмического поиска; автоматизированно
  проверено 0,8%;
- `calibrate` выдаёт диагностический score, а не поверенное измерение SNR;
- `robust` повышает накопленную энергию символа, но пока не исправляет ошибки;
- CI workflow в репозитории — механизм проверки, а не доказательство успешного
  прогона до появления результатов GitHub Actions.

## Вывод

Не следует начинать с замены 4-FSK на OFDM или с красивого спектрографа. Первый
настоящий качественный скачок дают потоковый audio engine, короткие физические
кадры, robust control channel, FEC и selective repeat. Они превращают текущую
«передачу WAV» в соединение, способное обнаруживать, переживать и объяснять
ошибки канала.

Порядок реализации и критерии готовности описаны в [ROADMAP.md](ROADMAP.md).
