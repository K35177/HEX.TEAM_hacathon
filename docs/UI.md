# Выбор UI-стека

## Почему был выбран Tkinter

Tkinter выбран для версии-прототипа как тонкий одностраничный frontend:

- modem, protocol, hashing, WAV и безопасная запись файлов выполняются в C++;
- UI только выбирает параметры и запускает тот же CLI;
- нет Chromium, Electron, web server и отдельного frontend build toolchain;
- один Python-файл легко проверять и менять, не дублируя бизнес-логику.

Поэтому скорость Python не ограничивает передачу: эфир длится секунды или минуты,
а DSP 0.5.0 декодирует такой сигнал в десятки миллисекунд. Замена кнопок на C++
не увеличит `goodput_bps`.

## Почему не C++ UI сейчас

C++ дал бы минимальный runtime overhead и self-contained binary, но стандартная
библиотека C++ не содержит кроссплатформенного GUI. FLTK, Qt, SDL/ImGui или три
native frontend требуют новой зависимости, упаковки и отдельной platform QA.
В текущей среде такой GUI toolkit не установлен.

Перенос UI на C++ имеет смысл после стабилизации streaming/protocol v2, если
измеренный бюджет установщика и памяти этого потребует. Слои проекта позволяют
заменить только frontend без изменения modem/transfer архитектуры.

## Почему не C#

C# удобен для Windows UI, но кроссплатформенный вариант потребует .NET runtime и
GUI framework вроде Avalonia. Это не улучшит PHY, FEC или delivery efficiency, а
добавит второй runtime и ещё одну систему сборки рядом с C++ core.

## Ограничение текущего решения

Tkinter требует Python 3 с модулем Tk. Исправлен Windows launcher fallback:
приложение предпочитает рабочий `python.exe`, а не наличие `py.exe`, которое само
по себе не гарантирует зарегистрированный interpreter. Для production остаются
два честных варианта:

1. упаковать проверенный Python/Tcl/Tk runtime в installer;
2. заменить только UI на компактный C++ frontend после измерения реальной цены
   обоих вариантов.

До появления installer UI нельзя называть полностью автономным.
